# Cache Hardening Requirement

**日期：** 2026-04-05
**分支：** `refactor/cache`
**运行模式：** `vibe / interactive_governed`

## 目标

在当前 `refactor/cache` 分支对现有缓存实现做一轮“正确性优先、粒度细化、语义收口”的整改，针对已识别的 8 个问题按阶段落地，并在每个阶段完成后进行独立提交。

## 交付物

- 一套按阶段执行的缓存整改方案与实施记录
- 修正公开表单可见性与博客预生成边界的代码
- 更细粒度的缓存标签与失效链
- 更一致的审核配置缓存读取语义
- 更清晰的后台缓存 keyParts 与读取入口
- 每个阶段对应的验证结果与 Git 提交
- `vibe` 运行产物与执行计划文档

## 问题范围

1. 公开表单列表泄露 `members` 可见性的表单存在性
2. `generateStaticParams()` 复用博客列表查询，受 `LIMIT 20` 影响
3. 公开博客/表单缓存 tag 粒度过粗
4. 审核配置接口存在“规则缓存 + 字段直查”的混合新鲜度
5. 缓存层异常兜底过宽，真实故障会被伪装成空数据
6. 多个 `unstable_cache` 的 `keyParts` 语义不清晰
7. 失效链按功能块整刷，缺少实体级失效边界
8. `getAdminFormById` 已实现但未被后台读取路径使用

## 约束

- 所有更改仅在 `refactor/cache` 分支完成
- 本次以缓存边界整改为主，不顺带重构无关业务
- 每完成一个阶段必须先验证，再提交
- 提交采用 Conventional Commits，中文描述
- 优先保证 Vercel/Next.js 16 下的构建稳定性

## 验收标准

- `members` 表单不再通过公开列表泄露存在性
- 博客预生成参数来源与列表展示来源解耦
- 公开博客与表单缓存具备实体级 tag 或等效精细化边界
- 博客、表单、审核相关失效逻辑与缓存读取语义一致
- 非预期数据库错误不会再被统一吞掉并伪装成正常空结果
- 后台缓存 key 与读取路径更可追踪、可维护
- 每个阶段至少完成 `bun run lint`
- 至少在阶段 1 和最终阶段完成 `bun run build`

## 非目标

- 不把所有后台 `unstable_cache` 全量迁移成 `use cache`
- 不重构认证体系、页面布局和无关 API 设计
- 不在本次内处理缓存之外的 UI/业务问题

## 已确认执行方式

本次按三个阶段依次执行：

1. 正确性与边界修正
2. 缓存粒度与失效链细化
3. 维护性与一致性收口

每个阶段完成后立即提交，确保中途可回滚、可审查。
