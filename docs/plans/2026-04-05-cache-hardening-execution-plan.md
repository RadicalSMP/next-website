# Cache Hardening Execution Plan

**日期：** 2026-04-05
**关联需求：** `docs/requirements/2026-04-05-cache-hardening.md`
**内部执行等级：** `L`
**执行方式：** 串行阶段执行，每阶段验证并提交

## 目标摘要

围绕当前缓存实现的 8 个问题，先修 correctness 和权限边界，再细化 tag 与失效链，最后清理可维护性问题，避免一次性扩大改动面。

## 阶段划分

### 阶段 1：正确性与边界修正

**阶段目标：** 先修会影响访问边界、预生成边界和排障可见性的问题。

#### 问题 1：公开表单列表泄露 `members` 表单

- 现状：
  `getActiveForms()` 仅按 `status = 'active'` 查询，公开 `/forms` 页面直接渲染结果。
- 计划：
  拆分“公开可展示表单列表”和“按 slug 取单表单详情”的职责，确保公开列表默认只返回允许公开展示的表单。
- 任务：
  新增或重构公开列表读取函数，使其明确表达公开展示规则。
  检查 `/forms` 页面与 `/api/forms/by-slug/[slug]` 的权限语义是否一致。
  明确 `authenticated` 与 `members` 两类表单在公开列表中的期望行为。
- 验证：
  公开列表不再出现不应公开展示的 `members` 表单。
  详情接口仍保留登录与成员校验。

#### 问题 2：博客预生成参数来源被列表查询限制

- 现状：
  `generateStaticParams()` 复用了带 `LIMIT 20` 的 `getPublishedPosts()`。
- 计划：
  拆出专门的“预生成 slug 查询”入口，避免把列表展示策略绑定到构建期 prerender 策略。
- 任务：
  新增预生成 slug 查询函数。
  让博客列表页继续使用列表查询，详情页预生成只依赖 slug 清单查询。
  保持默认 `dynamicParams` 行为不变，避免扩大渲染策略变更。
- 验证：
  构建期 prerender 清单不再受博客列表条数限制。
  博客列表行为保持不变。

#### 问题 5：缓存层异常兜底过宽

- 现状：
  `getActiveForms()`、`getReviewScoringRules()` 对异常处理过宽，会吞掉真实故障。
- 计划：
  只保留可证明必要的兼容兜底，其他异常显式抛出或至少保留可诊断语义。
- 任务：
  识别哪些 catch 是为了“迁移前缺表兼容”，哪些已进入正常运行期。
  收紧或删除过宽兜底。
  确保调用方不会因语义变化出现不可控崩溃。
- 验证：
  非预期数据库错误不再统一伪装成空数据。
  正常路径结果保持兼容。

**阶段 1 提交建议：** `fix(cache): 修正公开列表与博客预生成边界`

### 阶段 2：缓存粒度与失效链细化

**阶段目标：** 让公开缓存从“整块刷新”过渡到“列表 + 实体”分层失效。

#### 问题 3：公开博客/表单缓存 tag 粒度过粗

- 现状：
  博客公开侧统一使用 `blog-posts`，表单公开侧统一使用 `forms`。
- 计划：
  引入实体级 tag，并区分列表 tag 与详情 tag。
- 任务：
  为博客设计列表 tag 和按 slug 的实体 tag。
  为表单设计列表 tag 和按 slug 的实体 tag。
  调整公开详情与 metadata 读取函数的 tag 使用方式。
- 验证：
  单篇博客更新不会无谓打掉所有详情缓存。
  单个表单更新不会无谓打掉所有表单详情缓存。

#### 问题 4：审核配置接口混合缓存新鲜度

- 现状：
  规则读取走缓存，字段定义直查数据库。
- 计划：
  统一审核配置接口的缓存边界，让一个响应中的规则与字段属于同一失效语义。
- 任务：
  决定 `formFields` 是进入缓存读取，还是整个配置接口统一直查。
  若进入缓存，则设计对应 tag 与失效逻辑。
  若直查，则评估是否需要取消规则缓存或重新组合读取层。
- 验证：
  更新审核配置或表单字段后，不会返回混杂世代的数据。

#### 问题 7：失效链仍偏整块刷新

- 现状：
  `invalidateBlogCache()`、`invalidateFormCache()`、`invalidateSubmissionCache()` 仍以区块级 tag 为主。
- 计划：
  让写操作按影响范围精确失效：列表、实体详情、后台列表分别处理。
- 任务：
  梳理博客创建、更新、删除对哪些缓存面有影响。
  梳理表单创建、更新、删除、提交流程对哪些缓存面有影响。
  梳理审核评分、审核决定、审核规则更新的失效边界。
- 验证：
  失效函数与 tag 命名一一对应。
  不再存在明显“为了一个实体改动而整块刷新”的路径。

**阶段 2 提交建议：** `refactor(cache): 细化公开缓存标签与失效链`

### 阶段 3：维护性与一致性收口

**阶段目标：** 收口后台缓存语义，减少调试歧义和实现分叉。

#### 问题 6：`unstable_cache` 的 `keyParts` 语义不清晰

- 现状：
  多个后台缓存入口使用较笼统的 keyParts 名称。
- 计划：
  统一命名模式，让 key 一眼能看出所属域、列表/详情性质和关键维度。
- 任务：
  设计统一命名规则。
  调整博客、表单、审核、用户缓存 keyParts。
  确认不会与现有 tag 语义混淆。
- 验证：
  后台缓存入口具备统一命名风格。

#### 问题 8：`getAdminFormById` 未被后台读取路径使用

- 现状：
  缓存函数已存在，但后台单表单接口仍直接查库。
- 计划：
  统一后台单表单读取入口，避免缓存设计与实际调用路径脱节。
- 任务：
  让后台单表单 GET 路由使用缓存入口，或删除无效缓存入口。
  检查相关失效逻辑与单表单详情缓存是否一致。
- 验证：
  后台单表单读取路径与缓存设计一致。

**阶段 3 提交建议：** `refactor(cache): 统一后台缓存语义与读取入口`

## 所有权边界

- `lib/cache/*`：缓存实现、tag 命名、失效函数
- `app/(site)/blogs/[slug]/page.tsx`：博客预生成参数入口
- `app/(site)/forms/page.tsx`：公开表单列表使用的读取函数
- `app/(api)/api/forms/*`、`app/(api)/api/blog/*`、`app/(api)/api/forms/review/*`：写路径失效链与配置读取一致性
